# ROS1 重规划对比与 186 CPU 实测

日期：2026-10-12（北京时间）。任务：比较原作者 ROS1 与当前实现的重规划和资源占用，解释翻新飞机正在规划约5米路径时的10% CPU。

## 结论

当前186运行的是独立Odin入口，`service_only=false`。输入齐全后默认10 Hz每轮重新完整搜索，没有复用旧轨迹的触发判断。原作者在云更新后先检查旧轨迹，仅遇到不安全点才进入规划；目标事件也可触发规划。在目标不变、旧路径仍安全时，原策略省掉重复A*，从调度机制看明显更节省CPU。没有运行同输入同参数的ROS1/ROS2 A/B，不能给出两版实际CPU百分比或声称精确加速倍数。

现场只读采样确认：规划节点约0.85核，即8核整机的10.6%；相同目标在12秒里成功搜索120次，每次搜索平均82.03ms。重复搜索与当前CPU占用高度吻合，是首要优化方向。搜索耗时是墙钟时间，不能当作准确的CPU分项剖析；没有采集函数级性能剖析。

## 重规划差异

| 行为 | 固定ROS1 | 当前ROS2独立入口 |
| --- | --- | --- |
| 触发 | goal回调可直接plan；cloud回调建树后replan | goal/cloud更新输入；定时器调用plan |
| 已有有效轨迹 | 每隔40个旧Path点调用isSafe；安全则不搜索 | 每轮仍调用完整search，无旧路径有效性触发门槛 |
| 到达附近 | 实际起点距目标<0.3m，cloud触发的replan早退 | wrapper没有相同到达早退条件 |
| 执行索引节流 | 有time_index时，绝对索引差<10则plan早退 | 不使用外部time_index，不做相同节流 |
| 重新规划初态 | 初次/无index用实际输入；有index用旧Path index+3与差分速度 | 每轮实际odom位置/速度 |
| 初始加速度模式 | 先init=true，NO_PATH时再init=false | 始终init=false；首轮自由加速度分支 |
| 无目标 | 原源存在未初始化目标等问题，不保证语义 | 发布等待状态，不进入search |

源码定位：ROS1 wrapper L70–81、L101–129、L143–229、L244、L331、L364–389、L419–425、L464；当前wrapper L98、L247–271。

ROS1的40点步长配合0.01s输出采样，大致是每0.4s轨迹检查一次；它检查整个旧路径，不按已执行部分裁剪。原源的目标去重涉及未初始化`prev_goal`，不能把它解读为可靠的目标去重协议。原源还存在vy/vz下标错误、Path点数加一与越界等已知问题，不能直接复制全部状态逻辑。

## 单次搜索和地图成本差异

1. 当前普通0.6s原语采样数为`ceil(0.6×sqrt(3)×2/0.05)=42`。ROS1为端点位移`dist<SAFE_DIST`时1次，否则`ceil(dist/(2×SAFE_DIST))`；SAFE_DIST=0.45m、速度参数相同时普通原语在合法速度包线内一般为1–3次。当前每条完整通过的原语明显增加KDTree查询数，但不能据此直接推算整个搜索的耗时倍数。失败原语会提早结束，扩展数量和候选路径也不同。
2. ROS1 shot按`t_d/10`推进检查，约10次；当前shot按时长、速度上限及collision_step确定更密的采样，并额外校验动力学与边界。半径也不同：原版0.45m，当前0.25m，所以不是同等几何条件的公平对照。
3. 两版都保留两棵KDTree、每bank50帧、0.1m体素；不是每50帧才建树，而是每个接受的云更新都滤波并重建当前bank。只改重规划调度不会消除这项持续成本。
4. 原作者wrapper还按原始点序每2点取1点，并裁剪到当前位置各轴±20m。当前wrapper没有这两个步骤；186上游另有`down_samp_exe.py`，因此不能把原始输入点数或处理链当作相同。
5. 当前成功结果构造Path、采样p/v/a、曲线系数并进行消息发布，也有成本；现场没有分离建树和序列化的CPU占比。

源码定位：ROS1core L24–75、L329–345、L578–580；ROS1header L37；当前core L77–109、L236–254、L308–324、L513–522；当前wrapper L287–336。

## 186现场测量

先读取`/proc`采样8秒，没有新增ROS订阅；然后订阅结果、点云和里程计12秒。使用进程CPU时间差除以单调墙钟时间，避免`ps %CPU`启动以来平均值的误导。ROS观察器本身不计入规划进程CPU，但可能改变DDS发送成本，因此保留两个阶段的数字。

| 指标 | 结果 |
| --- | --- |
| 无观察器规划进程CPU | 84.86%单核 = 0.8486核 = 10.61%整机 |
| 有观察器规划进程CPU | 85.02%单核 = 0.8502核 = 10.63%整机 |
| 规划进程RSS | 60.48 MiB |
| 结果数/频率 | 120次/12.02秒，9.98Hz |
| 搜索状态 | 120次均REACH_END，无失败 |
| goal_revision | 全部3，没有新目标事件 |
| search平均/P50/P95/max | 82.03 / 81.35 / 87.17 / 88.20ms |
| 输入点云频率/平均点数 | 10.23Hz / 5847点 |
| 地图平均/最大点数 | 18148 / 18768点 |
| 每次输出采样点数 | 213 |
| 实际位置 | 首尾均近原点，变化远小于1mm |

`82.03ms×9.98Hz≈819ms搜索墙钟/秒`，与约849ms进程CPU/秒相近，支持“持续完整搜索主导负载”的判断；两者不是可直接相减的精确CPU分账。测量中的整机所有进程总繁忙率约45.73%，包含Odin、降采样、RViz、远程桌面等；用户的10%与规划进程折算整机百分比吻合，不代表整机全部程序的总负载只有10%。

## 主工程服务模式与建议

Task38正式桥启动`service_only=true`、`latest_observation`，不启用独立10Hz全搜索定时器。控制层有执行中的曲线时请求VALIDATE_TRAJECTORY，尚无曲线时请求PLAN；桥负责unknown检查和地图版本协调。因此不能将当前独立入口的10%直接归因到正式桥的同一种重复搜索策略。

建议首先让独立入口复用现有轨迹：目标事件/无可用轨迹时规划；云更新时验证剩余轨迹；失效才重规划，并保留实际p/v接入。可利用现有MotionAdapter的离散剩余曲线检查，避免额外设计整套执行索引协议。暂不通过扩大collision_step、稀疏取点或降低检查标准获取表面降耗。

本次只完成对比与诊断，没有修改算法、配置、部署、服务状态，也没有解锁或起飞。未执行ROS1同机场景A/B、函数级CPU剖析或优化后验收；无法承诺优化后的绝对CPU值。没有实施`agent/task`待办内容。
